# PLAN: Measure the model's real context window instead of guessing it

## Summary
Loom budgets its coder and planner agents against a user-configured context-window number that may have nothing to do with what the locally-hosted model actually accepts. When a run dies because the prompt filled the real window, the session halves its working number and retries — repeatedly, per run, re-learning the same lesson from scratch every session. This plan replaces guess-and-halve with measurement: probe Ollama for the model's true context length before the first request, give every long-running agent one shared overflow-recovery path (including hard provider rejections, not just empty generations), and reconcile Loom's own token estimates against provider-reported usage so silent server-side truncation and hidden token growth surface before things break. It also closes the blind spot that made any of this hard to diagnose: compaction currently runs — or fails to run — without saying a word, so the plan makes every compaction announce itself, in the log and in the chat feed, with the estimated token counts either side of it.

## Background & Context

Loom is a self-hosted coding-agent tool: FastAPI + Dishka + TortoiseORM/PostgreSQL backend built on Pydantic AI, driving planner/coder/reviewer agents through a WebSocket-controlled FSM (`backend/services/session_fsm.py`, `backend/api/v1/agent_session.py`). Models are typically local via Ollama's OpenAI-compatible endpoint.

What exists today, and why it produces the reported symptom ("The model had no room to reply … Retrying with 64,024", repeating with each halving):

- **The warning is Loom's own**, emitted by `AgentSession._narrow_after_overflow()` (`backend/api/v1/agent_session.py:679`). `_run_coder_streaming()` (`agent_session.py:778–812`) catches `UnexpectedModelBehavior`, checks it with `looks_like_no_room_to_answer()` (`backend/services/compaction.py:174` — matches 'token limit' + 'before any response', pydantic-ai's wrapper for an empty response with a length finish reason), halves the working window via `narrowed_window()` (`compaction.py:191`), and retries the entire `agent.run()`.
- **The narrowed window lives only on the session object** (`agent_session.py:706`). The `Task` row keeps the originally configured value, and every new session starts over at the configured number — hence halving warnings repeating periodically across runs/sessions.
- **The budget denominator is a guess.** `build_compaction()` (`compaction.py:217`) builds a five-tier `TieredCompaction` ladder (`DeduplicateFileReads` → `ClampOversizedMessages` → `ClearToolResults` → `SummarizingCompaction` → `SlidingWindowCompaction`) with `target_fraction=0.7` against an explicit `context_window`. `model_settings()` (`backend/services/model_resolution.py:11`) sends `num_ctx` to Ollama through `extra_body` — a request, not a guarantee: Ollama clamps it to what the model was trained for, and non-Ollama OpenAI-compatible servers ignore it entirely.
- **Fixed overhead is invisible to compaction.** Roughly 5,470 tokens of system prompt + sixteen tool schemas ride on every request (`estimate_fixed_overhead()` in `backend/services/context_budget.py`). On the first request of a run there is no history to trim, so when overhead + prompt alone exceed the real window, no amount of compaction can help. The prior plan's eighth field report established exactly this: five consecutive halvings failed identically, proving the overflow was never the conversation.
- **A guard already stops useless narrowing**: `context_window_complaint()` (`context_budget.py:47`) fires when window < overhead + `WORKING_HEADROOM_TOKENS` (4,096), and `_narrow_after_overflow` stops halving and surfaces it. `_warn_if_context_is_too_small()` (`agent_session.py:1223`) runs the same check proactively at session start.
- **Measurement precedent already exists**: `EmbeddingService.describe_model()` / `_model_info()` (`backend/services/embedding.py:198, 239`) POST to Ollama's native `/api/show` and read `model_info["<architecture>.context_length"]`, tolerating missing keys by returning None. `config_controller.py` queries `/api/tags` similarly. The chat-model path has no equivalent today.
- **Planner paths lack overflow recovery.** `_plan_structured()` (`agent_session.py:1008`) catches *all* exceptions from the structured attempt and falls back to `_plan_as_text()` (`agent_session.py:1052`), which has no recovery at all — an overflow there fails the session. Only the coder path narrows and retries.
- **Provider-reported usage is available but unused for calibration.** Per the pydantic-ai-harness compaction documentation (https://pydantic.dev/docs/ai/harness/compaction/), token estimates anchor on provider-reported usage of the most recent response when one exists; `ReportContextUsage` (already wired via `build_usage_monitor()`, `compaction.py:280`) reports against the *configured* window and cannot contradict it.
- **Compaction has one gate, not five.** `TieredCompaction` deliberately bypasses each tier's own trigger — *"Each tier's own trigger is bypassed -- `TieredCompaction` drives the tiers directly via their `compact` method and decides when to stop"* (`_tiered_compaction.py:41`). One gate at `target_fraction` × window decides *whether* to compact; escalation cheap-to-expensive then happens *within* that single event, re-measuring after each tier. Consequence: the `max_fraction=TARGET_FRACTION` / `context_window=window` arguments `build_compaction()` passes to `ClearToolResults`, `SummarizingCompaction` and `SlidingWindowCompaction` (`compaction.py:246`) are inert — they configure triggers that are never consulted. They are misleading, not harmful; the mechanism itself (ladder order, recent-message and tool-pair protections, `ask_user` exclusion, first-user preservation) is sound.
- **Compaction is invisible when it does fire.** The library announces a compaction only as a `compact_messages` OpenTelemetry span, started on `ctx.tracer` — a no-op tracer unless core instrumentation is active, which Loom never wires. There is no log line, no event, and no feed message. Even a correctly firing ladder shows up only as an unexplained drop in the `ContextUsageEvent` gauge, which is precisely why "is compaction even running?" could not be answered by looking. The library's own correction bookkeeping (`get_compaction_reclaim`, `_COMPACTION_RECLAIM` in `compaction/_shared.py`) is private and must not be read from Loom.
- **The public seam for observing it is a capability.** `TieredCompaction.before_model_request(ctx, request_context)` is public, as are `estimate_context_tokens` / `estimate_token_count` (exported from `pydantic_ai_harness.compaction`). A Loom-owned `AbstractCapability` that measures `request_context.messages`, delegates to the wrapped ladder, and measures again observes every compaction exactly, using nothing private.
- **Compaction is rare by design, and stays rare.** No `message_history=` is ever passed to `agent.run()` and each plan step is its own run, so the ladder only ever sees one step's fresh ReAct loop (cross-run memory flows through prompts built from `ConversationHistory` instead): it has to exceed the target *within a single step* to fire at all. Phase 1 makes the target reachable and therefore honest; it does not make compaction frequent, and the observability added in Phase 4 will most often report nothing — that is success, not a broken feature.
- **Adjacent dead code, noted not fixed.** `response_allowance()` (`compaction.py:158`) is never called: `model_settings()` deliberately omits `max_tokens`. Together with the inert per-tier arguments above, this is cosmetic debt worth clearing opportunistically; neither is a requirement of any phase.
- **The wire vocabulary is generated and drift-tested in both directions.** `MessageType` (`schemas/agent_messages.py`) feeds `protocol_vocabulary()` (`backend/protocol_export.py`), exported to `frontend/src/lib/protocol.generated.json` by `python scripts/export_protocol.py`. `backend/tests/test_protocol_export.py` compares the file on disk against the enums, and `frontend/src/lib/protocol.test.ts` compares the frontend's Zod options against the same file. Adding a member without regenerating fails the backend suite; regenerating without adding the Zod member fails the frontend suite. Both sides therefore have to land in one commit.
- **How an event becomes a line in the feed.** An event on the bus (`services/event_bus.py`) is converted by `to_message()` (`schemas/agent_messages.py`) into a `BaseAgentMessage`, validated on arrival by `schemas.ts`, and folded into state by `receive()` in `frontend/src/lib/stores/agent.ts` — either through a special path (`system` replaces a keyed slot, `context_usage` updates the gauge and never joins the feed, `thought` grows an existing bubble) or through the generic append path. Appearance comes from `typeStyles` and `MARKDOWN_TYPES` in `chatPresentation.ts`, and `ChatMessage.svelte` renders the type name itself as the bubble's label. `TaskRecorder` records only the events it has an entry type for and silently ignores the rest, so a new event is not persisted to the task log unless `TaskLogEntryType` gains a member — which this plan does not do (it would be a migration).
- **Tests**: backend suite at `backend/tests/`; relevant files include `test_execution_loop.py` (overflow/narrowing behaviour, including existing tests pinning the halve-and-retry semantics), `test_compaction.py` (ladder + `resolve_context_window`/`narrowed_window`), `test_context_budget.py`, `test_model_resolution.py` (patterns for monkeypatching `OLLAMA_BASE_URL`), `test_embedding.py` (`MockTransport` pattern for faking `/api/show`). Tests run against a real Postgres when `TEST_DATABASE_URL` is set; suites needing external services skip otherwise.
- Both `backend/AGENTS.md` and `frontend/AGENTS.md` (both mandatory) exist; see Global Rules. The frontend one matters from Phase 4 onward. The previous plan document (eight completed phases covering compaction introduction, step execution, etc.) has been replaced by this document at the user's direction; its findings survive in the Background sections above.

## Goal / Desired Behavior

1. Before the first request of a session, Loom knows — or soundly falls back — how large the serving model's context window actually is. For Ollama-served models it reads the model's context length from `/api/show`; the effective window used everywhere (compaction budget, usage monitor denominator, Ollama `num_ctx`) is the smaller of the user's configured number and that measurement.
2. When measurement is impossible (non-Ollama model name, unreachable server, unusable metadata), behavior is exactly today's — configured/default window plus halve-and-retry on failure — with no new warnings.
3. An overflow failure recovers identically on all three long-run paths (coder streaming, structured planning, text planning): narrow, retry the same call, stop at the existing complaint floor with the existing explanatory message. Hard provider rejections (HTTP 400-style context-length errors) are recognized as the same recoverable overflow, not as fatal crashes.
4. Divergence between what Loom estimated it sent and what the provider reports processing is detected during normal successful running: silently-truncated prompts (provider saw far less than sent) and unseen token growth (provider billed far more than estimated) each warn once per session with concrete numbers, and feed the working estimate so compaction targets reflect reality sooner.
5. Compaction stops being invisible. Whenever the ladder actually rewrites the history for a request, Loom says so: one log line and one message in the chat feed, each naming the run path and the estimated token counts either side of the compaction. A ladder that runs and changes nothing says nothing.
6. No database schema changes; reviewer/classifier agents untouched. Frontend work is confined to receiving and rendering the new compaction message.

### Phase 3: Reconcile Loom's estimate against provider-reported usage — Status: Not Started
- **Goal:** Use the provider's own accounting, available on every successful response, to catch the two failure precursors a success can legitimately reveal: silent input truncation (provider processed far less than Loom sent — small models clamping `num_ctx`) and hidden token growth (provider billed far more than Loom's heuristic sees — content invisible to the char-based estimator).
- **Requirements:**
  - [ ] After each successful model response on a long run, compare the provider-reported prompt/input token count against Loom's own estimate of what that request carried (fixed overhead from `estimate_fixed_overhead()` plus the estimated history at send time — reuse whatever accounting the compaction/monitor path already computes rather than recounting).
  - [ ] Classify divergence in both directions with named constants for the thresholds (chosen sensibly, e.g., provider-under ≲ half of estimate signals likely truncation; provider-over ≳ 1.5× signals unseen content — exact values are the agent's to tune and document):
    - Provider processed substantially *less* than sent → warn once per session that the model/server appears to be truncating input, naming the observed vs expected figures and pointing at `num_ctx`.
    - Provider processed substantially *more* than estimated → warn once per session that Loom's estimate understates reality, and feed the correction back so subsequent budgets account for it (e.g., adopt the larger observed figure into the working overhead/history accounting for the remainder of the session — the mechanism is the agent's choice; the requirement is that later requests budget against the corrected view).
  - [ ] Each direction warns at most once per session; subsequent divergences update the correction silently without new events, so the feed is never spammed.
  - [ ] Nothing here may change what is sent to the model mid-run other than the budget correction above; no history edits, no narrowing triggered by divergence alone (narrowing remains failure-driven from Phase 2).
  - [ ] The existing `ContextUsageEvent` contract and header gauge stay untouched.
- **Edge Cases & Error Handling:**
  - Runs shorter than two responses produce at most one comparison point — acceptable; the feature targets long ReAct loops.
  - Providers reporting zero/absent usage → skip reconciliation silently for that response.
  - Divergence caused by a Phase 2 retry boundary (fresh attempt after narrowing) must not double-warn; the once-per-session-per-direction rule covers it.
- **Affected Areas:** `api/v1/agent_session.py` (per-response hook on the streaming path and both planner paths), `services/context_budget.py` or `services/compaction.py` (threshold constants + correction helper), tests in `test_execution_loop.py` or a focused new module.
- **Acceptance Criteria:**
  - [ ] A synthetic run whose provider reports roughly half the estimated prompt tokens emits the truncation warning once with concrete numbers. — verified by: unit test with scripted usage figures.
  - [ ] A synthetic run whose provider reports ~1.5×+ the estimate emits the underestimate warning once and subsequent requests budget with the correction. — verified by: unit test asserting the adjusted budget reaches `build_compaction`.
  - [ ] Agreement within thresholds emits nothing new. — verified by: unit test.
  - [ ] Repeat divergences in the same session/direction add no further warnings. — verified by: unit test.
  - [ ] Existing suite green; `ContextUsageEvent` shape untouched. — verified by: pytest run + schema inspection.
- **Testing Notes:** Drive the comparison logic directly against synthetic (estimated, reported) pairs; wire-level coverage only needs one integration point asserted end-to-end.

### Phase 4: Make compaction visible, in the log and in the feed — Status: Not Started
- **Goal:** Whenever the compaction ladder actually rewrites a request's history, that fact reaches the log and the chat feed with the estimated token counts either side of it and the run path it happened on. Silence then means nothing was compacted, rather than meaning nobody can tell.
- **Requirements:**
  - [ ] Detect, per model request, that compaction rewrote the history. The seam is the implementing agent's choice among public-API options; the recommended one is a thin Loom-owned capability wrapping the ladder — implement `before_model_request`, estimate the tokens of `request_context.messages`, delegate to the wrapped `TieredCompaction`, estimate again, and report when the second figure is materially lower. `estimate_context_tokens` / `estimate_token_count` are exported from `pydantic_ai_harness.compaction` for exactly this. The alternative — inferring compaction from successive `ContextUsage` readings through the existing monitor — is acceptable if it proves cleaner in practice; document whichever was chosen and why.
  - [ ] Nothing private may be read to achieve this: not `compaction/_shared.get_compaction_reclaim`, not `_COMPACTION_RECLAIM`, not the `compact_messages` span. If the public surface turns out to be insufficient, stop and consult rather than reaching inside the library.
  - [ ] Keep the construction seam where it already is: `build_compaction()` returns the capability a run attaches, so let it return the observing wrapper (taking the reporting callback as a parameter) rather than making all three call sites assemble one themselves. Called without a callback it must behave exactly as today.
  - [ ] Report at most once per compacted request, and never for a ladder that ran and returned the history unchanged — a fired trigger whose tiers reclaimed nothing is not a compaction and must stay silent.
  - [ ] Emit one structured log line per occurrence through the module logger already used in `api/v1/agent_session.py`, naming the run path (coder streaming / structured planning / text planning) and both token figures.
  - [ ] Emit one event per occurrence carrying the figures as numbers, so the interface renders them instead of parsing them back out of prose: a `CompactionEvent` on the bus (`services/event_bus.py`), a `MessageType.compaction` member and a `CompactionMessage` in `schemas/agent_messages.py`, and the conversion in `to_message()`. Carry tokens-before, tokens-after (both `ge=0`) and the run path; follow the field-documentation style of `ContextUsageMessage`, which is the closest existing precedent.
  - [ ] No throttle and no once-per-session rule. Post-Phase 1 occurrences are expected to be rare, and each real compaction is information; the once-per-session discipline in Phase 3 exists because divergence repeats on every request, which this does not.
  - [ ] Regenerate the protocol artefact (`cd backend && python scripts/export_protocol.py`) and include it in the same commit as the enum member — `tests/test_protocol_export.py` compares the artefact on disk against the enums, so a stale file fails the backend suite.
  - [ ] Frontend: add the matching member to `schemas.ts`, extend the store's `MessageType` union, and give the message a case in the generic append path of `receive()` (`stores/agent.ts`) that words the line from the numbers — e.g. `Compacted the conversation to fit the context window — 21,300 → 12,840 tokens` — formatting the separators there, the way `describeSystem` builds its counter rather than shipping pre-formatted prose from the backend.
  - [ ] Frontend appearance: add a `typeStyles` entry in `chatPresentation.ts` visually distinct from both `system` and `warning`, because a compaction is routine housekeeping rather than a phase announcement or a fault. Decide `MARKDOWN_TYPES` membership deliberately: the content is a generated sentence carrying numbers and no markup, so plain text is the expected answer.
  - [ ] Compaction lines join the feed as ordinary appended messages: no `key` slot replacement (each compaction is its own event, and replacing the previous line would hide how often it happens), no effect on `pendingQuestion` / `status` / `requiresAction`, and the `ContextUsageEvent` gauge left exactly as it is.
  - [ ] Word the message for a reader who does not know what compaction is. It must read as "the conversation was shortened so it still fits", not as an error and not as jargon.
  - [ ] Observability may never cost a run: an exception raised while measuring, logging or emitting is caught and logged, and the request proceeds. Losing a step because a notice failed to send would be a worse bug than the blind spot this phase closes.
- **Edge Cases & Error Handling:**
  - The summarizing tier makes its own model call. That call must not report a compaction of its own — verify it carries no compaction capability, and exclude it explicitly if it does.
  - Two compactions in one run report twice; identical figures twice in a row are legitimate (the same step retried after narrowing) and must not be deduplicated.
  - A Phase 2 retry rebuilds the capability. A compaction on the attempt later abandoned still happened and is still reported; the feed showing it just before an overflow warning is correct rather than confusing.
  - The frontend treats an unknown message type as a systematic protocol mismatch rather than an isolated one, so a backend emitting `compaction` against a frontend that does not know it fails hard — which is why the artefact, the Zod member and the backend event all land in one commit.
  - Estimates, not truth: these figures come from the same ~4-characters-per-token heuristic compaction budgets against. Say "estimated" wherever the wording has room, and never present them as provider-counted tokens — Phase 3 owns those.
  - A compaction on the very first request of a run is possible when the prompt alone is large; nothing in the reporting may assume a previous request exists.
- **Affected Areas:** `services/compaction.py` (observing wrapper, its threshold constant, `build_compaction()` signature), `services/event_bus.py` (`CompactionEvent`), `schemas/agent_messages.py` (`MessageType.compaction`, `CompactionMessage`, `to_message`), `api/v1/agent_session.py` (reporting callback plus the three capability lists), `frontend/src/lib/protocol.generated.json` (regenerated, never hand-edited), `frontend/src/lib/schemas.ts`, `frontend/src/lib/stores/agent.ts`, `frontend/src/lib/chatPresentation.ts`; tests: `backend/tests/test_compaction.py`, `backend/tests/test_execution_loop.py`, `backend/tests/test_protocol_export.py`, `frontend/src/lib/protocol.test.ts`, `frontend/src/lib/schemas.test.ts`, `frontend/src/lib/stores/agent.test.ts`, `frontend/src/lib/chatPresentation.test.ts`.
- **Acceptance Criteria:**
  - [ ] A request whose history the ladder shrinks produces exactly one log line and exactly one `CompactionEvent`, carrying the run path and both token figures. — verified by: unit test driving the wrapper with a stub inner strategy that returns a shorter history.
  - [ ] A request the ladder leaves unchanged — under target, or tiers that reclaimed nothing — produces no log line and no event. — verified by: unit tests for both shapes.
  - [ ] All three long-run paths report compaction. — verified by: tests asserting the capability each path attaches, using the recording stand-in pattern already in `test_execution_loop.py`.
  - [ ] An exception thrown by the reporting callback does not fail the request. — verified by: unit test with a raising callback.
  - [ ] `to_message()` converts `CompactionEvent` into `CompactionMessage` with the figures intact. — verified by: unit test.
  - [ ] The regenerated artefact contains `compaction` and `test_protocol_export.py` passes. — verified by: pytest run after regeneration.
  - [ ] The frontend validates the message, appends exactly one feed line containing both formatted figures, and the protocol drift test passes. — verified by: vitest run.
  - [ ] `chatPresentation.ts` has a style for the new type, distinct from `system` and `warning`. — verified by: the presentation test asserting every `MessageType` has an entry.
  - [ ] Backend and frontend suites green beyond the Phase 0 baselines; `ContextUsageEvent` and the gauge untouched. — verified by: pytest + vitest + schema inspection.
- **Testing Notes:** Backend — drive the wrapper directly with a fake inner strategy rather than a live model; what is under test is the before/after comparison and the reporting decision, not the ladder. Frontend — feed the store a raw JSON payload exactly as `stores/agent.test.ts` already does for the other message types, and assert on the appended message rather than on rendered DOM wherever a store-level assertion suffices.

## Definition of Done
- Every phase's Status is Done — all Requirements and Acceptance Criteria checkboxes checked, each with a verification note.
- The backend test suite passes with no regressions relative to the Phase 0 baseline; `mypy . && basedpyright .` clean. The frontend suite passes with no regressions relative to its own Phase 0 baseline, and `npm run check` and `npm run lint` are clean.

## Open Questions
- **Exact divergence thresholds and correction mechanics (Phase 3):** intentionally left to the implementing agent's judgment with the recommended starting points stated in the requirements; document the chosen values in the phase summary rather than asking mid-flight, unless real usage data suggests the defaults are badly wrong.
- **Shared `/api/show` parsing seam (Phase 1):** extract-from-`embedding.py` vs new standalone module — agent's judgment; whichever keeps `EmbeddingService` behavior byte-identical (its own tests must pass unmodified).
- **Compaction detection seam (Phase 4):** the observing wrapper around `TieredCompaction` is the recommendation, with `ContextUsage`-delta inference as the fallback — the agent's judgment, documented in the phase summary. Settled and not open: the notice reaches the interface as its own `compaction` message type carrying the counts as numbers, rather than as a reworded `system` announcement.
- **Modelfile `num_ctx` preference (Phase 1):** if reading the tighter of parameters-vs-architecture proves unreliable across Ollama versions, fall back to the architecture context length alone and note it in the summary — this is latitude, not a blocker.

## Non-Goals / Explicit Exclusions
- No persistence of the discovered or effective window anywhere (no columns, no settings writes) — explicitly declined by the user; revisit as future work if wanted.
- No frontend work beyond the compaction message: the settings UI, the context gauge and every existing event contract stay as they are.
- No tier-level attribution of a compaction (which rung of the ladder reclaimed the tokens) — that needs the harness's span and receipt internals, which are private. Noted as future work.
- No OpenTelemetry or tracer wiring: the observability added here is a log line and a WebSocket message, nothing more.
- No persistence of compaction notices to the task log (`TaskLogEntryType` gains no member, so no migration) — a compaction is interesting while the session runs, not afterwards.
- No cleanup of the dead `response_allowance()` or of the inert per-tier `max_fraction`/`context_window` arguments inside `build_compaction()` — recommended opportunistically, required by no phase.
- No changes to reviewer/classifier agents or to the compaction ladder's composition.
- No support for non-Ollama local servers' metadata endpoints in this pass.
